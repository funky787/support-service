# Отчёт по проекту 

## Что сделал

За время практики разработал REST API для обработки заявок в техническую поддержку.

Основную часть написал на Java и Spring Boot. Для хранения данных использовал PostgreSQL, а для создания таблиц — Flyway.

В приложении можно создавать заявки, редактировать их, менять статусы, просматривать историю изменений и искать заявки по фильтрам.

Отдельно на Kotlin реализовал статистику за выбранный период. Она показывает количество заявок, распределение по статусам и приоритетам, просроченные заявки и среднее время решения.

## Kotlin

Kotlin используется в `ReportService.kt` и `SummaryResponse.kt`.

Для модели ответа использовал `data class`, чтобы не писать вручную дополнительные методы.

В расчётах применил `mapNotNull` и nullable-тип `Double?`. Если завершённых заявок нет, среднее время возвращается как `null`.

Java-контроллер вызывает Kotlin-сервис, который использует Java-репозиторий для получения данных.

## Тестирование

Для тестирования использовал JUnit, Mockito и Testcontainers.

Проверял создание заявок, правила смены статусов, ошибки API, историю изменений, фильтрацию и статистику.

Интеграционные тесты работают с PostgreSQL, который запускается через Testcontainers.

По последнему сохранённому отчёту JaCoCo:

- Покрытие инструкций — 91%.
- Покрытие ветвей — 83%.

Во время проверки обнаружил ошибку фильтрации `overdue=false`: заявки без срока выполнения не попадали в результат.

Исправил условие в `TicketService.java`, добавил регрессионный тест и оформил изменение через Pull Request.

Подробности находятся в `docs/defects.md`.

## Docker и база данных

Для запуска приложения подготовил Dockerfile и Docker Compose.

В Docker запускаются Spring Boot и PostgreSQL. Данные базы хранятся в отдельном volume и сохраняются после перезапуска контейнеров.

Также проверил резервное копирование базы и восстановление данных в отдельную тестовую базу.

Для проверки работоспособности используются health checks.

## GitHub Actions

Настроил автоматическую проверку, сборку и развёртывание приложения.

Pipeline состоит из трёх этапов:

- `verify` — проверки и тесты;
- `publish` — сборка Docker-образа и публикация в GHCR;
- `deploy` — развёртывание приложения на Ubuntu.

Для деплоя использовал self-hosted Runner на виртуальной машине.

После успешных проверок GitHub Actions автоматически публикует образ с тегом по SHA коммита и запускает его на Ubuntu.

## Трудозатраты

Практика рассчитана на 72 академических часа.

Работа была разделена на анализ требований, проектирование, разработку Java API, интеграцию Kotlin, тестирование, настройку Docker, CI/CD и документацию.

Плановое распределение часов приведено в `docs/specification.md`. Отдельный фактический учёт времени по каждому этапу не вёлся.

## С какими проблемами столкнулся

При запуске Gradle возникала ошибка совместимости Java 25 с используемыми инструментами. Для проекта настроил Java 21.

При тестировании пришлось настраивать Testcontainers и PostgreSQL.

Также настраивал GitHub Runner на Ubuntu, подключение к Docker и автоматическое развёртывание приложения.

Во время проверки API нашёл и исправил ошибку фильтрации непросроченных заявок.

## Ограничения проекта

В проекте нет отдельного графического интерфейса и авторизации пользователей. В рамках задания реализована серверная часть, которую можно проверять через Swagger UI.

Приложение запускается как один сервис с отдельной базой PostgreSQL. Разделение на микросервисы не предусмотрено.

## Результат

В итоге получилось работающее REST API с PostgreSQL, статистикой на Kotlin, автоматическими тестами и CI/CD.

Работоспособность подтверждена тестами, результатами GitHub Actions и проверкой приложения на Ubuntu.
