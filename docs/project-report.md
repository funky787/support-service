# Отчёт по проекту 

## Что сделал

За время практики разработал REST API для работы с заявками в техподдержку.

Основную часть написал на Java и Spring Boot. Данные хранятся в PostgreSQL, для создания таблиц использовал Flyway.

В приложении можно создавать заявки, редактировать их, менять статусы, просматривать историю и искать заявки по фильтрам.

Отдельно на Kotlin сделал статистику за выбранный период. Она показывает количество заявок, распределение по статусам и приоритетам, просроченные заявки и среднее время решения.

## Kotlin

Kotlin используется в `ReportService.kt` и `SummaryResponse.kt`.

Для ответа использовал `data class`, чтобы не писать вручную конструктор и остальные методы.

Также использовал `mapNotNull` для обработки времени закрытия и nullable-тип `Double?`. Если решённых заявок нет, среднее время возвращается как `null`.

Java-контроллер вызывает Kotlin-сервис, а тот получает данные из Java-репозитория.

## Тестирование

Написал модульные и интеграционные тесты. Использовал JUnit, Mockito и Testcontainers.

Проверял создание заявок, переходы статусов, ошибки API, историю изменений и статистику.

Интеграционные тесты запускаются с настоящим PostgreSQL в Docker.

Все проверки прошли успешно через:

`.\gradlew.bat clean check jacocoTestReport`

По последнему отчёту JaCoCo получилось:

- Покрытие инструкций — 91%
- Покрытие ветвей — 83%

При проверке нашёл ошибку с фильтрацией `overdue=false`: заявки без срока выполнения не попадали в результат.

Исправил условие в `TicketService.java`, добавил регрессионный тест и отправил изменения через Pull Request #1.

Подробнее ошибка описана в `docs/defects.md`.

## Docker и база данных

Для приложения сделал Dockerfile и Docker Compose.

В Docker запускаются два контейнера: Spring Boot и PostgreSQL. Данные базы хранятся в отдельном volume, поэтому после перезапуска не пропадают.

Также проверил создание резервной копии PostgreSQL и восстановление данных в отдельную тестовую базу.

## GitHub Actions

Настроил автоматическую сборку и развёртывание приложения.

Pipeline состоит из трёх этапов:

- `verify` — запуск проверок и тестов
- `publish` — сборка Docker-образа и загрузка в GHCR
- `deploy` — установка новой версии на Ubuntu

Для деплоя использовал self-hosted Runner на виртуальной машине Ubuntu.

После объединения Pull Request приложение автоматически обновилось на сервере. Проверка `/actuator/health/readiness` вернула `UP`.

Также проверил откат на предыдущий Docker-образ и возвращение к актуальной версии. Оба запуска прошли успешно.

## С какими проблемами столкнулся

При запуске тестов Gradle сначала использовал Java 25, из-за чего возникала ошибка совместимости. Переключил окружение на Java 21.

Были проблемы с запуском Testcontainers, поэтому пришлось поправить настройки зависимостей и Docker.

При настройке деплоя отдельно устанавливал и запускал GitHub Runner на Ubuntu, настраивал Docker и подключение приложения к PostgreSQL.

## Результат

В итоге получился работающий REST API с базой данных, тестами, статистикой на Kotlin и автоматическим развёртыванием.

Отдельного пользовательского интерфейса в проекте нет, проверять запросы можно через Swagger.
