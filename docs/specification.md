# Спецификация Support Service

## О проекте

Support Service — это REST API для обработки заявок в техническую поддержку.

Идея проекта в том, чтобы заявки не терялись и можно было отслеживать их состояние. Для каждой заявки сохраняются категория, приоритет, срок выполнения и история изменения статусов.

## Кто будет пользоваться

- Сотрудник — создаёт заявку и проверяет её состояние.
- Специалист поддержки — обрабатывает заявки и меняет статусы.
- Руководитель — смотрит статистику по заявкам.

В проекте реализован только сервер с REST API. Отдельного интерфейса и авторизации нет, для проверки используется Swagger.

## Пользовательские истории и критерии приёмки

**1. Создание заявки**

Как сотрудник, я хочу создавать заявки, чтобы сообщать о технических проблемах.

Критерии:
- Если заголовок и категория указаны, сервер возвращает HTTP 201.
- Новая заявка получает статус `NEW`.
- Если обязательные поля не заполнены, возвращается HTTP 400.

**2. Просмотр заявки**

Как сотрудник, я хочу просматривать заявку по ID, чтобы узнавать её состояние.

Критерии:
- Существующая заявка возвращается с HTTP 200.
- Если заявки нет, возвращается HTTP 404.

**3. Изменение статуса**

Как специалист поддержки, я хочу менять статус заявки, чтобы отмечать ход работы.

Критерии:
- Разрешены переходы `NEW → IN_PROGRESS → RESOLVED`.
- Заявку можно отменить из `NEW` и `IN_PROGRESS`.
- Запрещённый переход возвращает HTTP 409, не изменяя заявку и историю.

**4. Редактирование заявки**

Как специалист поддержки, я хочу изменять данные заявки, чтобы уточнять информацию.

Критерии:
- Можно менять описание, приоритет и срок выполнения.
- Закрытую или отменённую заявку редактировать нельзя.
- При попытке изменить закрытую заявку возвращается HTTP 409.

**5. Поиск заявок**

Как специалист поддержки, я хочу фильтровать заявки, чтобы быстрее находить нужные обращения.

Критерии:
- Работают фильтры по статусу, категории, приоритету и просрочке.
- Поддерживается пагинация.
- В результате возвращаются только заявки, соответствующие условиям поиска.

**6. Статистика**

Как руководитель, я хочу получать статистику за период, чтобы оценивать работу техподдержки.

Критерии:
- Отчёт показывает количество заявок и распределение по статусам и приоритетам.
- Отображаются просроченные заявки и среднее время решения.
- Если завершённых заявок нет, среднее время возвращается как `null`.

## Правила работы заявок

Приоритеты:

- `LOW`
- `MEDIUM`
- `HIGH`

Возможные переходы статусов:

- `NEW → IN_PROGRESS`
- `NEW → CANCELLED`
- `IN_PROGRESS → RESOLVED`
- `IN_PROGRESS → CANCELLED`

Закрытую или отменённую заявку нельзя открыть заново.

Заявка считается просроченной, если срок выполнения уже прошёл, а статус остался `NEW` или `IN_PROGRESS`.

При изменении статуса запись в историю сохраняется в той же транзакции.

## API

| Метод | Адрес | Для чего |
|---|---|---|
| POST | `/api/tickets` | Создать заявку |
| GET | `/api/tickets` | Получить список |
| GET | `/api/tickets/{id}` | Получить заявку по ID |
| PUT | `/api/tickets/{id}` | Изменить заявку |
| PATCH | `/api/tickets/{id}/status` | Изменить статус |
| GET | `/api/tickets/{id}/history` | История статусов |
| GET | `/api/categories` | Список категорий |
| GET | `/api/reports/summary` | Статистика за период |

Пример создания заявки:

`POST /api/tickets`

`{"title":"Не работает принтер","categoryId":2,"priority":"HIGH"}`

`
{
"id": 1,
"title": "Не работает принтер",
"description": null,
"categoryId": 2,
"priority": "HIGH",
"status": "NEW",
"createdAt": "2026-11-15T12:00:00Z",
"dueAt": null,
"closedAt": null
}
`

В ответ возвращается HTTP 201 и созданная заявка со статусом `NEW`.


Пример получения заявок с фильтрацией:

`GET /api/tickets?status=NEW&priority=HIGH&page=0&size=10`

Пример запрещённого перехода:

Если заявка находится в статусе `NEW`, попытка сразу перевести её в `RESOLVED` возвращает HTTP 409.

Пример статистики:

`GET /api/reports/summary?from=2026-01-01T00:00:00Z&to=2027-01-01T00:00:00Z`

Период включает начальную дату, но не включает конечную.

## Техническая часть

Основная логика написана на Java и Spring Boot. Для хранения данных используется PostgreSQL, миграции выполняются через Flyway.

Статистика реализована на Kotlin в том же приложении.

Для тестирования используются JUnit, Mockito и Testcontainers.

Приложение запускается через Docker Compose. Данные сохраняются после перезапуска контейнеров. Ошибки API возвращаются в едином формате. Пароли и другие секреты не должны храниться в репозитории.

## Диаграммы

Для проекта подготовлены две диаграммы:

- `er.mmd` — структура базы данных и связи между таблицами.
- `process.mmd` — процесс обработки заявки и переходы статусов.

Обе лежат в папке `docs`.
